# Step16 fixed non-symlink compiler-candidate selection procedure contract

## Status, predecessor, and present boundary

This is a repository-only design/review contract and deterministic repository-text test. It is not a helper implementation, host procedure, command sequence, candidate inspection, metadata probe, compiler invocation, build, or authorization for any live action. It binds the immediate published predecessor exactly to `36c1e8ef82d6d4f75df3a1ad9dbc2d5084c936e5`; no branch, successor, tag, working tree, caller, environment, configuration, or supplied value may substitute that predecessor. The predecessor is historical design input only, never current authority.

The predecessor's terminal classification of `/usr/bin/cc` as a symlink remains an opaque terminal rejection. This contract does not reuse, resolve, target through, disclose a target of, or otherwise follow `/usr/bin/cc`. It selects no current candidate, path, compiler, target, owner, mode, digest, identity, command, argument, environment, repository root, or operational action.

## One-record candidate selection authorization

A later candidate-selection package may consider exactly one proposed absolute compiler-entry path only after an explicit human-approved candidate authorization record exists. The proposal source and rationale must be human supplied in that record; this contract does not supply, select, infer, guess, or enumerate any candidate. The record must bind all of the following exact fields: a durable unique opaque record ID separate from approval ID; one canonical absolute entry path; its separately bound canonical parent path; its separately bound exact single basename; the human-supplied proposal source and rationale; scope exactly `single non-dereferencing entry metadata probe`; exact approved context; issuance time; expiry time; reviewer identity; approval ID; and fixed stop conditions. The durable opaque record ID, consumption binding, and approval ID are distinct values and no selected store, identifier algorithm, clock implementation, or live time is chosen by this design.

The exact absolute candidate-path grammar is canonical: it begins with `/`; has no empty or repeated separators; has no `.` or `..` component; has no trailing slash; and contains no whitespace or control character. The separately bound canonical parent path and exact single basename must be derived only from that canonical entry path. The basename must not contain `/`; the entry relation is exactly one relative basename beneath that bound parent, not a broader relative path, alternate parent, recomposed pathname, or reconstructed path. This grammar validates only a proposed record field and does not select a path now.

A trusted clock must validate issuance and expiry before any use. Before any later host probe, a durable atomic consume-before-probe reservation transition must bind the record's durable opaque record ID to that exact approved canonical entry path, canonical parent path, single basename, scope, and context. The transition must complete before the host gate or any host probe and must reject concurrent, in-flight, replayed, already reserved, already consumed, completed, failed, expired, crash/restart, uncertain transaction, or uncertain state use. The record cannot be used unless that durable consumption binding states its exact approved path, scope, and context; no later probe may treat approval ID, a copied record, or a partial binding as consumption. This design chooses no durable store, transaction algorithm, or live trusted-clock source now.

The fixed stop conditions are: absent, malformed, substituted, ambiguous, expired, replayed, already reserved, in-flight, already consumed, already completed, failed, inaccessible, unsupported, unreviewed, unapproved, missing required field, missing durable opaque record ID, missing trusted-clock validation, missing or non-atomic consume-before-probe reservation, crash/restart or uncertain transaction/state, missing exact consumption binding, scope expansion, path-grammar violation, parent/basename mismatch, directory selection or listing, generic candidate selection, symlink classification, any resolution attempt, any target-derived fact, and any attempted live action. A candidate authorization record cannot be refreshed, copied, replayed, broadened, or substituted; a new candidate requires a new human proposal and a new explicit human approval.

The record must not choose a candidate from current runtime defaults, PATH, environment, configuration, caller input beyond the explicit human record, package-manager query, directory contents, globbing, `which`, `command -v`, a previously rejected link, target-derived data, or an alternate repository root. It must not list directories, scan entries, resolve paths, call `readlink`, resolve a target, or guess a compiler. It must never target through the pre-existing `/usr/bin/cc` symlink.

## Separate later host gate and stop-on-symlink boundary

Candidate selection authorization authorizes neither a probe nor any host access. Before any later metadata probe, a separate explicit host gate, separate review, and separate authorization must approve that one record without modification. This contract contains no helper implementation and no host command snippets.

A later probe must authenticate and retain a parent FD for exactly the separately bound canonical parent path, then pass only the separately bound exact single basename as the entry to Linux `openat2` with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`. The entry must be exactly that one relative basename. No parent, basename, entry, path, relation, substitution, recomposition, reconstruction, or broad relative-path input is permitted. Linux `openat2` unavailability, unsupported flags, missing, released, unauthenticated, or wrong-parent FD, any resolution error, pathname reopen, descriptor-to-path conversion, ordinary `openat`, compatibility behavior, retry, or fallback fails closed. A symlink is an opaque terminal rejection with no target resolution, disclosure, retention, hash, metadata, approval, or expansion of scope.

Only a regular-entry metadata result from that later separately authorized probe may be reported, and it is non-authoritative. It cannot compile, invoke a compiler or helper, build, activate, select a target, read headers, access filesystem contents, access an endpoint or secret, perform RPC, sign, send, deploy, commit, publish, or authorize any further action. Successful candidate selection or metadata collection never supplies execution, source, repository, network, key, or operational authority.

## Independent canonical repository-root boundary

Before any later source authority, a distinct future separate root authorization record must independently select and verify one accessible canonical repository root. It must bind the exact canonical root path using the same canonical absolute-path grammar; retained-FD non-symlink component-authentication facts for that exact root; a durable root identity token or record; issuance time; expiry time; trusted-clock validation; reviewer identity; approval ID; and the exact root-to-record binding. The root record and its durable identity are separate from the candidate record and approval, and no selected store, token algorithm, or live time is chosen by this design.

The root must be independently selected and verified with no alternative root, ambiguity, caller root, CWD, worktree, environment, configuration, predecessor, metadata, candidate record, prior inaccessible root, access condition, or test result substitution. This contract does not authorize repository-root access, authentication, inspection, change, or source authority.

Any missing, stale, malformed, substituted, generic, directory-derived, target-derived, reused, inaccessible, unapproved, unreviewed, symlinked, unsupported, path-reopened, fallback, caller-controlled, root-substituted, missing durable root identity, missing retained-FD non-symlink component authentication, missing separate root record, missing root-to-record binding, or ambiguous condition is a non-echoing fail-closed refusal. This repository-only contract authorizes no host probe, compiler/helper execution, build, header activation or read, filesystem/content access, endpoint/secret access, RPC, signing, sending, deployment, commit, or publication.
